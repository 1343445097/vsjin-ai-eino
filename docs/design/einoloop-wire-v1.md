# VSJin EinoLoop Wire v1 (implementation contract)

One trusted backend connection; no business/model credentials in model prompts or the independent engine. HRSS remains owner of identity, model invocation, tool authorization, chat history and audit. Fast path unchanged. CLI retained.

Configuration: HRSS `HRSS_EINO_LOOP_BASE_URL` and `HRSS_EINO_LOOP_API_TOKEN`; VSJin `VSJIN_AI_API_TOKEN` must match. Explicit Eino expert binding must fail clearly if not configured; do not silently change engine.

POST `/v1/runs`, Authorization Bearer service token, Content-Type application/json. Body:
```
{"version":"1","runId":"uuid","runToken":"random-secret-per-run","messages":[{"role":"system","content":"authorized system and skill catalog"},{"role":"user","content":"..."}],"tools":[{"type":"function","function":{"name":"skills_read","description":"...","parameters":{"type":"object",...}}}],"initialToolCalls":[{"id":"bootstrap-skill","type":"function","function":{"name":"skills_read","arguments":"{\"skill\":\"conversation-image-understanding\"}"}}],"maxIterations":12,"timeoutSeconds":180,"temperature":0.2}
```
`messages` is standard LLM message JSON (role/content/name/tool_calls/tool_call_id; tool_calls OpenAI-style id/type/function{name,arguments}). In wire v1, `content` remains a string for text-only messages and may be an ordered content array for user text and inline images:

```json
{"role":"user","content":[
  {"type":"text","text":"请识别图中标高"},
  {"type":"image_url","image_url":{"url":"data:image/png;base64,iVBORw0KGgo...","detail":"high"}}
]}
```

Content array parts are exactly `{ "type":"text", "text":"..." }` or `{ "type":"image_url", "image_url":{ "url":"data:image/{png|jpeg|webp};base64,...", "detail":"auto|low|high" } }`; `detail` is optional. Part order is preserved. External URLs, other media types, unknown part fields/kinds, malformed or non-canonical base64, and images in non-user messages are rejected. At most 4 images are allowed in one message, each decoded image is at most 8 MiB, and encoded image data across one run request is at most 16 MiB. Text content across a run request remains at most 4 MiB. Run requests and emitted events are bounded by 24 MiB; text-only response callbacks retain the 4 MiB body limit. Image payloads are kept in memory only; the runtime performs no filesystem access. Errors are generic and never include image bytes.

The runtime advertises `features:["model.delta","message.images","tool.bootstrap"]` on `run.started`. HRSS must retain `message.images` when relaying user content to the model and must not claim image support if the capability is absent. `tool.bootstrap` means the runtime accepts optional `initialToolCalls`, an ordered array of at most two standard `schema.ToolCall` objects. Each call must use `type:"function"`, a unique valid ID, a declared function name, and valid object-shaped JSON arguments. Arguments cannot contain image fields/data URLs or raw identity fields. After `run.started`, the runtime emits each call through the ordinary authorized `tool.request` callback before its first `model.request`, then places one assistant tool-call message and matching tool observation messages into the model history. A failed callback is represented by the sanitized observation `{"isError":true,"error":"bootstrap tool failed"}` and does not prevent the model from describing the failure. If `initialToolCalls` is absent or empty, execution follows the existing path unchanged. Text-only v1 remains backward compatible: existing scalar `content` values keep the same JSON representation, including omission of empty content.

Response SSE each `data: <json>`. Every event has `version:"1",type,runId,sequence`.
- `run.started`: runtimes may advertise `features:["model.delta","message.images","tool.bootstrap"]`. HRSS streams model output only after `model.delta` is present. It sends image content only when `message.images` is present and sends `initialToolCalls` only when `tool.bootstrap` is present; older runtimes that omit a feature retain their prior behavior.
- `model.request`: requestId plus `messages` and `tools` arrays. HRSS calls existing authorized LLMClient, audits input/output and posts response below. Original user image parts remain ordered and present in subsequent model requests, including the final answer request after tool rounds. No API key/address in event.
- `tool.request`: requestId plus `call:{id,type:"function",function:{name,arguments}}`. HRSS invokes EXISTING per-run tool invoker; runtime must only accept declared tools. Tool may be skills_read or skill_http_request; schema and tool scope remain HRSS-owned.
- `message.delta`: `delta` string. A capable runtime may emit multiple ordered chunks while the final HRSS model request is still running. `run.completed.final` must equal their concatenation. If no chunks were sent, HRSS emits the complete final answer as one compatibility delta.
- `run.completed`: `final` string, MUST nonempty final assistant after all tools.
- `run.failed`: `error` sanitized string.
- `run.cancelled`.

POST `/v1/runs/:runId/responses` Authorization service token AND `X-VSJin-Run-Token: runToken`. Body `{"requestId":"...","message":<standard assistant message>}` for model, `{"requestId":"...","delta":"visible answer chunk"}` for a model delta, `{"requestId":"...","result":"tool result"}` for tool or `{"requestId":"...","error":"sanitized failure"}`. Deltas are nonempty, apply only to the matching pending model request, retain its request ID, and do not complete it; HRSS follows them with exactly one complete assistant message. Exactly one final reply is accepted; repeat/unknown replies rejected 409. 204 success. HRSS reads the runtime SSE concurrently with the model callback so deltas reach the session before model completion. Tool-enabled model rounds remain whole-response callbacks. POST cancel `/v1/runs/:runId/cancel`, same two tokens; HTTP context cancellation also cancels the run. No arbitrary callback URL/SSRF. Ended run discarded, duplicate active runId returns409. Run request and emitted event bodies are limited to 24 MiB; response callback bodies remain limited to 4 MiB. A run's text content is limited to 4 MiB and its encoded image data to 16 MiB. Whole run is bounded by its timeout and iteration budget.

Runtime interface on HRSS side can match existing Run(ctx, []*schema.Message, emit AgentEvent)(*LLMResponse,error), SetAuditRecorder, SetForceFirstTool, SetReturnDirectlyTools if needed. External engine remains stateless; same authorized tools/history supplied each run. Service-token binding required even on localhost for `/v1/runs*`.

`maxIterations` bounds model-generation rounds, including the final answer. The last allowed round exposes no tools and asks the model to summarize available evidence and limitations. If a tools-enabled decision round returns content without tool calls, runtime spends the reserved next round on a tool-free final answer so ordinary no-tool answers can use real streaming safely. A one-round budget is answer-only. Business-tool errors return structured `isError:true` result observations while retaining failed audit artifacts; undeclared tools, invalid protocol, model failures and cancellation remain terminal failures. No error is converted into fabricated successful evidence.

Streaming answer normalization trims leading/trailing whitespace incrementally and removes an explicit leading, closed `<think>...</think>` envelope (or a leading orphan closer followed by a Markdown heading). An unclosed leading thinking envelope produces no visible answer and fails. Model reasoning belongs in the separate reasoning field or this explicit envelope. Literal markers in the visible body are preserved; a streaming reply cannot retract previously emitted text using the whole-response legacy heuristic. Older whole-response callbacks retain that heuristic. The streamed concatenation and final answer must agree exactly.

Final answer instructions are coalesced into one system message at the beginning of model history. The original user question is repeated at the end as text-only content, preserving every text part while leaving its original image parts only in their original history position. An image-only question gets a short text generation prompt; its original image remains exactly once. This keeps the final request compatible with providers that require leading system messages and lets HRSS authorize the unchanged image multiset. This internal generation request is not persisted as a new business-user turn.
